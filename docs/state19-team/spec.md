# Team Lead 长期小组 Spec

## 背景

state17 的 SubAgent 是一次性委派：任务完成即结束，主 Agent 必须在中转位置上接收所有结果，
子 Agent 之间无法直接协作。state18 已提供 worktree 文件隔离，但还没有「长期存在的团队」
概念：没有共享任务板、没有邮箱、没有队员生命周期，也没有 Lead 的派发/终止/收口职责。
结果是多个成员即使能并行，也只能各自与主 Agent 单线沟通，主 Agent 成为信息瓶颈。

本阶段把主 Agent 升级为 Team Lead，建立长期小组、共享任务板与邮箱，让成员直接协作；
成员在独立 worktree 中并行工作。终端独立进程、跨进程上下文恢复、git 合并与 coordinator
模式按两阶段切分留到 state20。

## 目标

1. **主 Agent 升级为 Team Lead**：常驻一套 Lead 编排工具，能创建/加载长期小组，拆解用户
   目标、建任务、派生成员、终止成员、收发消息。
2. **建立长期小组对象**：记录组名、负责人、成员花名册、持久化位置；成员记录角色、
   工作目录、运行后端、是否需要审批。
3. **成员并行且文件隔离**：state19 的成员以同进程协程运行，每人绑定独立 worktree；
   成员之间通过共享任务板和邮箱直接协作，不经过 Lead 中转。
4. **共享任务板**：任务支持创建/读取/更新/删除、指派、依赖字段；依赖完成后才可领取；
   Lead 可指派，成员可抢未指派任务。
5. **邮箱协作**：名称注册表 + 每成员邮箱文件；消息含发件人、正文、时间戳、已读、摘要；
   支持点对点、广播与五类结构化协议消息。
6. **审批闭环**：需审批成员在每个任务开始前提交计划，Lead 以结构化 decision 批准/驳回；
   超时转 blocked，绝不偷偷开干。
7. **成员生命周期**：成员执行完当前工作后标记 idle 并通知 Lead；同进程内 Lead 再发消息
   可唤醒继续；进程重启后团队与记录仍在，成员显示 offline。
8. **持久化与并发安全**：小组落在用户目录下按组名分文件夹；邮箱读写用锁文件，拿不到锁
   重试，锁过旧视为过期。

## 已确认范围决策

- 采用两阶段切分：state19 做团队与协作内核；state20 做独立终端后端、跨进程恢复、
  git 合并与 coordinator 双锁模式。
- 主 Agent 常驻 Lead 工具，可自主建组/派活；用户可通过命令查看与切换当前小组。
- 每个成员绑定独立 worktree（复用 state18），成员记录中保存路径与分支。
- 任务依赖采用「领取门控」：依赖未完成不可领取；只拒绝自依赖，不做环检测与自动调度。
- Lead 可指派任务，成员也可领取未指派任务（原子领取）。
- 需要审批的成员按任务粒度提交计划；Lead 决定批准/驳回；等待超时转 blocked。
- 结构化消息采用五类最小集：`text`、`broadcast`、`plan_request`、`plan_decision`、`status`。
- 成员完成后进程内 idle + 内存恢复；磁盘上下文恢复留给 state20。
- Lead 与成员使用两套分离的工具面；普通子 Agent 与未组队主入口看不到成员协作工具。
- 小组与记录跨重启持久；未终止成员重启后为 offline，可重新派生（全新上下文）。
- 多组并存，存在「当前小组」；成员固定属于一个小组，跨组不可直接发消息。
- 消息在任务边界消费；运行中的任务不被普通消息打断。

## 功能需求

### F1 小组生命周期与持久化

- 用户可以创建、列出、查看、切换「当前小组」；同一用户下允许多个小组并存，成员固定属于
  一个小组，跨组不能直接发消息。
- 小组记录名称、负责人（Lead）、成员花名册、创建时间与持久化位置；持久化在用户目录下按
  组名分的独立文件夹中。
- 小组、成员元数据、任务板、邮箱在 CodePilot 重启后可重新加载；已结束的成员显示为 offline。
- 未指定当前小组时，Lead 的团队工具返回明确错误；不会隐式创建或猜测小组。

### F2 成员花名册与派生

- Lead 可派生成员，指定成员名、角色、运行后端、是否需要审批；成员名在组内唯一。
- 派生成员时为其分配独立工作目录与分支（复用 Worktree 隔离），并把绝对路径、分支写入
  成员记录。
- 派生成功后成员加入花名册；终止后成员留在花名册中并标记 terminated，不再接受消息或唤醒。
- 成员状态至少区分：spawning（创建中）、running（执行中）、idle（空闲）、blocked（等待
  审批/外部条件）、offline（进程重启后未恢复）、terminated（已终止）、failed（异常结束）。
- 进程重启后，未终止成员一律为 offline；Lead 可以重新派生同名 offline 成员，此时使用
  全新上下文（磁盘上下文恢复留给 state20）。

### F3 成员运行后端

- 成员记录运行后端；本阶段实现同进程协程后端。
- 允许显式指定后端，也允许自动选择；自动选择按确定的环境优先级执行，且必须把最终选择
  记录到成员元数据。
- 显式要求本阶段未实现的后端时，派生必须失败并给出明确原因；不允许静默替换为同进程后端。
- 自动选择无法满足强隔离预期时，必须通过日志与成员记录暴露实际后端，不得无提示降级。

### F4 工具面隔离

- Lead 拥有独立的编排工具面：创建/列出/切换小组、派生/终止成员、发送消息、创建/更新/
  查看任务、查看成员与任务状态。
- 成员在自己的会话中拥有协作工具面：任务增删查改与领取、点对点/广播消息。
- 普通子 Agent（非团队成员）与未组队的主入口永远看不到成员协作工具；成员也看不到 Lead
  的派生/终止等编排工具。
- 成员系统提示必须包含：所属小组、成员名、工作目录、分支、可用的协作工具，以及
  「任务边界消费消息」的约定。

### F5 共享任务板

- 任务字段至少包含：任务 ID、标题、描述、状态、负责人/指派对象、依赖任务 ID 列表、
  创建时间、更新时间。
- 任务状态至少包含：pending（未开始）、in_progress（执行中）、done（已完成）、
  cancelled（已取消）。
- Lead 可以创建任务、更新任务字段、指派成员、查看全部任务；成员可以创建、查看、更新、
  删除任务，并领取未指派任务。
- 领取规则：只有 pending、未指派、且所有依赖任务均为 done 的任务可被领取；领取是原子的，
  两个成员不能同时领到同一任务。
- 创建任务时只允许引用已存在的任务作为依赖；拒绝自依赖。
- 删除仍被其他任务依赖的任务必须被拒绝并说明原因。
- 任务板所有写入必须原子且并发安全；领取失败要返回具体原因（已被领取/依赖未完成/
  任务不存在）。

### F6 邮箱与名称注册表

- 消息投递采用两段式：先通过小组内的名称注册表把成员名解析为邮箱位置与状态，再写入目标
  邮箱。
- 每条消息包含：发件人、收件人、类型、正文、时间戳、是否已读、摘要。落盘时自动补时间戳、
  默认未读；摘要未提供时由正文自动生成。
- 支持点对点消息与广播；广播为该组每个目标成员各生成一份独立消息副本，已读状态互不影响。
- 邮箱写入使用锁文件保证并发安全：拿不到锁按策略重试；锁超过有效期视为过期并可被接管；
  仍失败则操作返回明确错误，不产生半写消息。
- 名称注册表同样受锁保护；成员不存在、已终止或跨组投递必须被拒绝。
- 消息默认在任务边界被消费：成员开始新任务、完成当前任务转空闲、或被唤醒时读取未读消息；
  运行中的任务不被普通消息打断。
- 审批等待是特例：成员在阻塞等待针对当前任务的 decision，只消费对应任务的 plan_decision。

### F7 结构化协议消息

至少支持五类消息：

- `text`：点对点普通正文。
- `broadcast`：群发正文。
- `plan_request`：成员向 Lead 提交计划，携带任务 ID 与计划正文。
- `plan_decision`：Lead 对计划作出决定，携带任务 ID、批准/驳回、理由。
- `status`：成员状态通知，携带状态值、任务 ID（可空）与备注。

所有结构化消息在落盘与读取时都要校验必填字段；非法类型或缺失字段的消息必须拒绝写入或
被明确标记，不得被当作普通文本静默处理。

### F8 审批闭环

- 成员是否需审批由成员记录决定；需审批成员对**每个任务**都必须在开始前提交计划。
- 流程：领取/收到任务 → 不开始工作 → 发送 plan_request → 阻塞等待 → 收到批准才开始；
  收到驳回则任务回到 pending、清除指派、成员回到 idle。
- 等待超时上限可配置；超时后成员转 blocked 并发送 status 通知 Lead，任务保持未开始；
  Lead 之后仍可发送 decision 或改派/终止。
- 未收到批准前，成员不得执行任何文件写入或任务相关工作；只允许读取消息、查看任务和
  提交计划。
- 非审批成员不进入该流程，收到任务后直接开始。

### F9 成员空闲、唤醒与终止

- 成员完成当前任务且没有更多已指派任务后，标记 idle，发送 status 通知 Lead，并保留进程内
  上下文。
- Lead 向 idle 成员发送消息时，成员被唤醒并继续使用同一上下文执行新指令；不需要重新派生。
- 成员异常结束标记 failed 并通知 Lead；被终止标记 terminated；进程重启后为 offline。
- 终止成员必须停止其协程、拒绝后续消息，并保留其工作目录与分支（不自动删除改动）。
- 终止、失败、blocked、idle 都必须可从成员状态与日志中观察到。

### F10 Lead 编排职责

- Lead 可以把用户目标拆成带依赖的任务写入当前小组的任务板，按成员角色与能力派生成员，
  并指派或允许成员领取任务。
- Lead 可以查看成员状态与任务板，向单个成员或全组发消息，终止成员。
- 所有任务完成或无法继续时，Lead 向用户报告：各成员结果、任务最终状态、遗留工作目录/分支。
- 本阶段 Lead 不做 git 合并、冲突解决与回滚；这些在 state20 交付。成员改动保留在各自
  worktree 中，Lead 只能报告路径与分支。

## 非功能需求

### N1 并发与一致性

- 任务板、名称注册表、成员元数据的写入必须原子化：要么完整可见，要么不可见，不产生
  半写记录。
- 邮箱追加使用锁文件保护；锁获取失败按策略重试，超时返回错误；过期锁可被安全接管。
- 同一小组内的任务领取、指派、状态变更必须无丢失更新：两个并发请求不能同时成功领取
  同一任务。
- 进程内团队操作必须线程/协程安全；跨进程场景以文件锁兜底（为 state20 的独立进程后端
  预留）。

### N2 安全与路径边界

- 小组名、成员名、任务 ID 等进入文件路径或消息路由的输入必须严格校验：拒绝空值、路径
  分隔符、`..`、绝对路径、Windows 保留名和越界解析。
- 所有持久化路径在真实解析后必须仍位于该小组目录内；不允许跨小组读写。
- 成员名解析、任务引用、消息收件人必须存在于当前小组；不存在、已终止、跨组一律拒绝并
  说明原因。
- 消息正文按用户目录明文持久化，属可接受设计；不得写入日志以外的敏感信息副本。

### N3 可观测性

- 小组创建/加载/切换、成员派生/终止/状态变化、任务创建/领取/完成/删除、消息投递/消费、
  审批请求/决定/超时都必须写结构化日志，包含小组、成员、任务或消息标识与结果原因。
- 后端选择结果、被拒绝的操作原因、锁重试与过期接管必须可观测，禁止静默处理。
- 用户可见错误必须说明「哪个操作失败、为什么、下一步怎么做」；不得只打印异常栈或
  泛化失败。

### N4 故障隔离与 fail-closed

- 单个成员失败、终止或消息处理异常不得中断 Lead 主循环或其他成员；失败成员标记 failed
  并通知 Lead。
- 损坏的任务/消息/元数据记录必须被隔离（跳过并报告），不得导致整个小组无法加载。
- 未实现的后端、无法获取邮箱锁、非法审批决定、未获批准就尝试开工，一律 fail-closed：
  明确拒绝，不自动降级、不猜测、不抢先执行。
- 成员被终止或 blocked 时不得继续执行任务；终止后不得再消费新任务或写入文件。

### N5 兼容性与架构边界

- 不改变进程工作目录（无 `chdir`）；沿用 state18 的显式绝对路径与 worktree 隔离，不新增
  全局路径缓存。
- 团队领域逻辑不得依赖 UI/Textual；成员协作工具不得进入普通子 Agent 的工具面。
- 未创建/未使用小组时，主 Agent 除新增的 Lead 工具外行为不变，不会自动创建小组、派发
  成员或写用户目录。
- 现有 730 项测试基线不得因本阶段下降；未涉及团队的既有路径无需修改断言即可通过。

### N6 可测试性

- 小组根目录、时钟、锁重试间隔/上限、审批超时、成员后端必须可注入，单元测试不依赖真实
  用户目录与真实等待。
- 任务依赖门控、领取竞争、消息锁、审批超时、成员状态机应实现为可独立测试的纯逻辑或
  可替换组件。
- 至少提供临时目录下的端到端测试：建组 → 建任务 → 派生成员 → 审批 → 完成 → 报告。

### N7 跨平台与规模边界

- 路径与文件操作使用跨平台语义（pathlib、原子替换）；Windows 下不假设 POSIX 锁或符号
  链接行为。
- 本阶段按单机、单进程、每组数十名成员、数百任务/消息的规模设计；不承诺大规模团队性能。
- 邮箱读取只返回未读消息或有界批次，避免消息文件增长导致上下文与内存无界膨胀；摘要
  长度有上限。
- 小组目录长期增长必须可通过删除小组/清理操作管理；本阶段至少提供明确的持久化位置与
  人工清理路径。

## 不做的事

以下内容在 state19 **明确不做**：

### 运行与生命周期

- 不做独立终端窗格/终端复用后端，不做窗格唤醒，不做真正的独立成员进程。
- 不做成员上下文跨进程从磁盘恢复；重启后成员为 offline，只允许以全新上下文重新派生。
- 不做成员在任务执行中途被消息打断、暂停、保存与恢复。
- 不做成员崩溃后的自动重启、自动补员或自动重新指派。
- 不做跨机器、跨网络、多用户共享团队。
- 不做成员同时属于多个小组。

### Lead 收口

- 不做 git merge/rebase/cherry-pick、跨 worktree 同步、冲突自动解决、冲突回滚上报。
- 不自动删除成员的 dirty worktree 或分支；只报告路径与分支，由 state20 与用户决定收口方式。
- 不做 coordinator 双锁模式、写文件工具剥夺、合并专属工具面。

### 任务与协作协议

- 不做环检测（仅拒绝自依赖）、拓扑排序、自动排队、自动解锁通知、优先级、截止时间、
  重试策略、任务配额。
- 不做成员之间互相审批；审批决定只能由 Lead 发出。
- 不做文件/图片等非文本消息、附件、流式增量消息、消息加密。
- 不做跨组消息、任务共享或成员借用。

### 界面与运维

- 不新增独立团队管理 TUI 面板；状态通过 Lead/成员工具结果、`/team` 命令输出与日志呈现。
- 不做自动扩缩容、成本预算控制、成员并发配额管理。
- 不做小组删除命令；本阶段提供明确的持久化位置与人工清理路径。

## 验收标准

### AC1（F1）小组生命周期

- 可创建至少两个小组并列出、查看、切换当前小组；成员固定属于其中一组。
- 重启 CodePilot 后，小组、成员记录、任务板、邮箱仍可加载，未终止成员显示 offline。
- 当前无小组时，Lead 团队工具返回明确错误，不自动创建小组。
- 验证方式：创建两个组 → 切换 → 重启 → 列表与成员状态符合预期。

### AC2（F2/F3）成员派生与后端

- 派生成员后花名册出现该成员，记录角色、工作目录绝对路径、分支、后端、是否需审批；
  对应 worktree 与分支实际存在。
- 显式指定未实现后端时派生失败并说明原因；自动模式选择同进程后端并把结果写入成员记录；
  无静默降级。
- 终止成员后其协程停止、不再响应消息，工作目录与分支仍保留。
- 验证方式：派生 → 检查磁盘与花名册 → 终止 → 再次发消息被拒绝。

### AC3（F4）工具面隔离

- Lead 会话可见编排工具，不可见成员协作工具；成员会话相反；普通子 Agent 与未组队主入口
  都看不到成员协作工具。
- 成员系统提示包含小组、成员名、工作目录、分支与协作约定。
- 验证方式：分别检查 Lead、成员、普通子 Agent 的实际工具列表与系统提示。

### AC4（F5）共享任务板

- Lead 可创建带依赖的任务并指派；成员可创建、查看、更新、删除任务，并领取未指派任务。
- 依赖未全部完成、任务已被指派、任务不存在时，领取被拒绝并说明具体原因。
- 两个并发领取只有一个成功；删除被依赖的任务被拒绝。
- 验证方式：构造依赖链与并发领取测试，检查返回与最终状态。

### AC5（F6）邮箱与名称注册表

- 点对点消息落盘后具备发件人、收件人、类型、正文、自动时间戳、默认未读、自动摘要。
- 广播为每个目标成员生成独立副本，已读状态互不影响。
- 锁被占用时按策略重试；过期锁可被接管；失败时不产生半写消息。
- 未知成员、已终止成员、跨组投递被拒绝。
- 消息在任务边界被消费，运行中的任务不被普通消息打断。
- 验证方式：并发写入、锁占用/过期、广播已读隔离、投递失败场景。

### AC6（F7）结构化协议消息

- 五类消息 `text`、`broadcast`、`plan_request`、`plan_decision`、`status` 均可写入、读取
  并保留结构字段。
- 非法类型或缺失必填字段的消息被明确拒绝，不被当作普通文本处理。
- 验证方式：逐类写入并读回；构造畸形消息断言拒绝。

### AC7（F8）审批闭环

- 需审批成员在收到/领取任务后先发 `plan_request`，在收到批准前不执行任何任务工作或
  文件写入。
- 批准后任务进入 in_progress 并开始执行；驳回后任务回到 pending、清除指派、成员回到 idle。
- 超过等待上限后成员 blocked 并发送 status，任务保持未开始；Lead 之后仍可发决定。
- 非审批成员不进入等待，直接开始任务。
- 验证方式：分别走批准、驳回、超时、非审批四条路径，检查状态与文件副作用。

### AC8（F9）空闲、唤醒与终止

- 成员完成任务且无更多指派时标记 idle，并向 Lead 发送 status。
- Lead 向 idle 成员发消息可唤醒，成员在同一进程内继续使用原有上下文，无需重新派生。
- 成员异常标记 failed；终止标记 terminated；进程重启后为 offline。
- 验证方式：完成 → 观察 idle/status → 再次指派 → 验证上下文连续；终止与失败路径分别检查。

### AC9（F10）Lead 端到端编排

- 给定一个用户目标，Lead 能拆出至少两个带依赖的任务，派生至少两个成员，完成指派/领取、
  一次审批、执行与完成报告。
- 最终报告包含各成员结果、任务状态、每个成员的工作目录与分支；本阶段不执行任何 merge。
- 一个成员失败时，其他成员与 Lead 仍能继续。
- 验证方式：临时用户目录下的端到端测试 + 一次真实 TUI 验收。

### AC10（N1/N2）并发、原子性与路径安全

- 并发任务领取、并发邮箱写入、并发元数据更新不产生重复领取、丢失更新或半写记录。
- 含路径分隔符、`..`、绝对路径、保留名的组名/成员名被拒绝；解析后逃逸小组目录的路径
  被拒绝。
- 跨组读写被拒绝。
- 验证方式：并发测试 + 表驱动非法名称/路径测试。

### AC11（N3/N4）可观测性与故障隔离

- 建组、派生、任务变更、消息投递、审批、终止、超时均产生结构化日志，失败含原因。
- 单个成员抛错、退出或消息损坏不影响 Lead 与其他成员；损坏记录被隔离并报告。
- 未获批准、后端不可用、锁失败等场景均 fail-closed，不发生静默降级。
- 验证方式：注入成员异常与损坏记录，检查主流程继续与日志/错误输出。

### AC12（N5/N6/N7）回归、架构与跨平台

- 全量测试通过且数量不少于基线 730；`ruff check .` 不新增告警。
- 代码中无 `os.chdir`；团队领域逻辑不 import UI/Textual；现有未涉及团队的测试无需弱化
  断言即可通过。
- 至少一个临时目录端到端测试覆盖建组→任务→派生→审批→完成→报告。
- 邮箱读取有界；Windows 下锁与原子替换可工作；路径处理无 POSIX 假设。
- 验证方式：`pytest`、`ruff`、代码审查、临时目录测试。
