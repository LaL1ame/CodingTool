# Team Lead 强隔离与收口 Spec

## 背景

state19 已把主 Agent 升级为 Team Lead：创建长期小组、派生同进程成员、共享任务板与邮箱、
审批闭环、消息在任务边界消费。但 state19 有三处明确交给后续的能力缺口：

1. **成员上下文不可跨进程恢复**：成员是长期存活 Agent，`_msgs` 只在进程内内存续接；
   重启后所有成员置 offline，Lead 重新派生同名成员只能用全新上下文，无法接续之前的任务记忆。
2. **不做 git 合并**：state19 明确"Lead 不合并、成员改动保留在各自 worktree，只报告路径/分支"。
   多个成员并行改完文件后，没有把成果汇总回主仓的机制。
3. **无 coordinator 模式**：Lead 的工具面与普通编排一致，没有"纯粹做编排、把写文件完全交
   给成员"的专注模式。

state20 补齐这三块，把团队协作从"能编排"推进到"能安全收口、能跨进程续接、能专注指挥"。

## 目标

1. **成员上下文跨进程恢复**：成员对话历史落盘，进程重启后 Lead 重新派生同名成员时自动恢复
   之前的记忆（若存在），实现"中断→重启→接着干"。
2. **git 合并与冲突处理**：Lead 能把多个成员 worktree 的成果汇总合并到团队汇聚分支，
   无冲突自动合并，有冲突安全回滚并上报，绝不破坏成员分支与主工作区。
3. **coordinator 专注模式**：通过"配置能力开关 + 用户环境变量"双锁开启；开启后 Lead 专心
   做派人/终止/审计划/发消息/合并，写文件完全交给成员。

## 已确认范围决策

- 采用两阶段切分：**state20** 做跨进程上下文恢复 + git 合并/冲突/回滚 + coordinator 双锁；
  **state21** 做独立终端窗格后端 + 窗格唤醒（Windows 可行性需先探针）。
- A2 跨进程恢复触发：**复用派生时自动恢复**——Lead 重新派生 offline 成员时若检测到持久化
  上下文则自动加载，否则全新。不新增独立恢复入口。
- A2 持久化内容：**仅对话历史**（成员 `_msgs` 落盘为 JSONL，复用 state12 会话格式）。
- A3 冲突策略：**无冲突自动合并；有冲突整体回滚（`git merge --abort`）+ 上报冲突文件清单**，
  交由 Lead/用户决策；不做 LLM 自动裁决冲突。
- A3 合并目标：合到**固定 team 汇聚分支** `codepilot/team/<team>/merged`，不动主工作区
  当前分支；合并前要求成员分支有完整提交。
- A4 coordinator 作用范围：**仅主 Agent(Lead) 的工具面**——削去 write/edit 等写文件工具，
  保留 read/grep/glob/run（run 用于跑 git 合并）+ team_* 编排工具；成员照旧写文件干活。
- A4 双锁生效表现：**削工具 + 注入 coordinator 模式提示**；两把锁缺一即保持 state19 行为。

## 功能需求

### F1 成员上下文跨进程持久化

- 成员的长期对话历史（`_msgs`）在以产生新对话轮次时持续追加落盘，格式复用项目现有的会话
  JSONL 存储（含 user/assistant/工具调用结构）。
- 每个成员一份独立的上下文文件，按小组与成员名隔离，不与主会话、其他成员混淆。
- 落盘写入是追加式的，失败不产生半行，不影响成员当前运行。

### F2 派生时自动恢复

- Lead 重新派生一个 offline 成员时，若存在该成员的持久化上下文，则用该历史**恢复**该成员的
  对话记忆（成员 launch 后能看到之前的消息与工具往返），而非以空上下文派生。
- 若不存在持久化上下文，则行为与 state19 完全一致（全新上下文派生）。
- 恢复后的成员仍按 state19 规则工作：绑定同一 worktree/分支，消息在任务边界消费，状态上报。
- 显式"清空旧上下文"或判为损坏的持久化文件：降级为全新上下文，不崩溃、不卡死。
- 进程内（非重启）的成员 idle/唤醒继续使用内存上下文，不受影响。

### F3 合并前成员改动落盘

- 成员在 worktree 的改动是未提交文件（state19 成员从不 git commit）。合并前，Lead 把每个
  参与合并成员的 worktree 改动**提交到该成员自己的分支**。
- 提交信息自动生成（可辨识的成员名 + 时间戳/任务主题）；提交动作对用户透明或可观察，不丢失
  成员改动。
- 只有有未提交改动的成员才产生新提交；无改动的成员分支保持原状。提交失败不中断整体，报告异常
  成员。

### F4 合并到汇聚分支

- Lead 可对当前小组发起合并：把多个成员分支合并进固定汇聚分支
  `codepilot/team/<team>/merged`（若不存在则基于主工作区当前 HEAD 创建）。
- 合并顺序确定（如按成员派生顺序）；主工作区当前分支不受影响。
- 合并前校验必要前提（汇聚分支可创建/检出、成员分支存在、无占用冲突），不满足则明确报错。

### F5 冲突检测与安全回滚

- 合并过程中，若存在 Git 不能自动合并的冲突，立即**放弃本次合并**（回滚到尝试前状态，
  等效 `git merge --abort`），保留各成员分支与主工作区原样。
- 回滚时上报冲突文件清单（哪些文件、涉及哪些成员分支），供 Lead/用户决策后续处理。
- 无冲突的合并完成，Lead 得到合并结果摘要（本次合入哪些分支、新增/修改文件数）。

### F6 coordinator 双锁与开关

- coordinator 模式由"配置能力开关"与"用户环境变量"两把锁共同开启：**两把都打开才生效**，
  任一关闭则保持 state19 行为（Lead 工具面不变）。
- 配置能力开关放在项目配置文件 `config.yaml` 的 `team:` 段（默认关闭）；用户环境变量可作为
  启动时覆盖（默认未设）。
- 生效时对 Lead 可见、可观察（日志/提示块），不静默。

### F7 coordinator 工具面收窄

- coordinator 生效时，主 Agent(Lead) 的工具面移除写文件类工具（write/edit 及同类
  side_effect 文件写工具），保留：
  - 读类工具（read/glob/grep）；
  - shell 执行（run——用于跑 git 合并）；
  - 团队编排工具（team_*：建组/派人/终止/发消息/审计划/任务/合并）。
- 成员与普通子 Agent 的工具面不受 coordinator 影响。
- Lead 系统提示注入 coordinator 模式说明：只负责编排与收口，文件修改必须交给成员。

### F8 合并工具

- Lead 具备一个团队合并工具（`team_merge`）：封装 F3–F5 的合并流程，返回结果或冲突报告。
- 工具在 coordinator 与非 coordinator 模式下都可用（合并属于编排职责）；非 coordinator 下
  使用不额外要求开启双锁。

## 非功能需求

### N1 安全与数据一致性

- 跨进程持久化使用原子写/追加，损坏文件隔离（不阻塞恢复，降级全新上下文并记录）。
- 合并操作要么整体成功、要么整体回滚，不残留半合并状态；绝不删除或改写各成员分支。
- coordinator 工具面收窄只影响主 Agent 的工具可见性，不改变成员/普通子 Agent 的能力。
- 双锁开关只做"是否开启 coordinator"，不作为权限绕过；用户仍可正常退出 coordinator。

### N2 可观测性

- 成员上下文已保存/正在恢复/降级全新、成员合并提交初、合并成功、合并冲突回滚/冲突文件清单、
  coordinator 开启/关闭，均写结构化日志。
- coordinator 开启时 Lead 可见明确提示，不开时无任何差异。

### N3 兼容性

- 未开启 coordinator、无待恢复上下文、无编辑意合并时，state19 全部既有行为不变。
- 现有测试基线不下降；未涉及团队/coordinator/合并的既有路径无需修改断言即可通过。
- 主工作区当前分支永远不被合并流程直接污染（只动汇聚分支）。

### N4 可测试性

- 跨进程恢复：临时 worktree + 临时上下文文件，可注入假 clock，验证"有上下文恢复/无则全新/损坏
  降级"三种路径。
- 合并：临时 Git 仓库构造多成员分支与未提交改动，验证无冲突合并、冲突回滚、汇聚分支创建、
  提交信息、回滚后状态。
- 双锁：配置段 + 环境变量四种组合（开开/开关/关开/关关），验证仅"开开"进入 coordinator；
  工具面收窄、提示注入可单测。
- 建立组 → 派生（含恢复）→ 多成员改文件 → 合并 → 冲突回滚的端到端临时目录测试。

### N5 跨平台

- 路径与 Git 调用使用参数列表、显式 cwd，无 shell 拼接、无 `chdir`。
- 合并与恢复不依赖 POSIX 专属行为；Windows/CI(Linux) 均可运行。

## 不做的事

- 不做独立终端窗格后端、窗格唤醒、真实独立成员进程（state21）。
- 不做跨机器、跨网络、多用户共享团队。
- 不做成员间实时流式通信。
- 不做 LLM 自动裁决合并冲突（冲突一律回滚上报，交 Lead/用户决策）。
- 不做合并策略选择（merge/rebase/cherry-pick 的 UI 切换）；本阶段固定用分支合并到汇聚分支。
- 不做跨进程协作状态（任务板/审批状态）恢复——那些本就持久化在团队存储；本阶段只恢复成员
  对话历史。
- 不做 coordinator 的 UI 面板；通过配置/环境变量 + 提示块呈现。

## 验收标准

### AC1（F1/F2）跨进程上下文恢复

- 成员完成任务产生对话后，其上下文已落盘；进程重启后 Lead 重新派生同名成员，该成员能回忆之前
  任务（消息/结论），而非从零开始。
- 无上下文时重新派生行为与 state19 一致；损坏上下文时降级全新且不崩溃。
- 验证方式：临时上下文端到端测试 + 真机重启后重新派生。

### AC2（F3）合并前成员改动落盘

- 有未提交改动的成员，合并前其 worktree 改动被提交到成员分支，提交信息可辨；无改动成员不产生
  新提交；提交失败只报该成员不停整体。
- 验证方式：临时 Git 仓库断言分支提交。

### AC3（F4/F5）合并与回滚

- 无冲突时合并到 `codepilot/team/<team>/merged`，主工作区当前分支不变；结果摘要正确。
- 有冲突时整体回滚，成员分支与主工作区原样保留，且上报冲突文件清单。
- 验证方式：临时 Git 仓库构造无冲突/冲突场景，断言汇聚分支、回滚与报告。

### AC4（F6/F7）coordinator 双锁

- 四种双锁组合中仅"配置开 + 环境变量开"进入 coordinator；其余保持 state19。
- coordinator 下主 Agent 无 write/edit 等写文件工具，保留 read/run/team_*；成员不受影响。
- 系统提示含 coordinator 说明；日志记录开启与否。
- 验证方式：单测四种组合 + 工具面断言 + 真机观察。

### AC5（F8）合并工具

- `team_merge` 可用，返回成功摘要或冲突报告；非 coordinator 下可用。
- 验证方式：Lead 工具集断言 + 临时仓库端到端。

### AC6（N1/N3）安全与回归

- 全量测试通过且数量不少于基线 918；`ruff check .` 不新增告警。
- 主工作区当前分支永不被合并流程污染；损坏上下文不阻塞恢复。
- 未开启 coordinator、无上下文、无合并时，state19 既有行为不变。

### AC7（N2/N4/N5）可观测与跨平台

- 恢复/保存/合并/回滚/coordinator 均产生结构化日志。
- 至少一个临时目录端到端测试：建组→派生→多成员改文件→合并→冲突回滚。
- Windows 与 CI(Linux) 均可运行；无 `os.chdir`，Git 用参数列表。
