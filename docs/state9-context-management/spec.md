# CodePilot 上下文管理 + Token 优化 Spec

## 背景

- CodePilot 是 ReAct 循环的 AI 编码助手。目前**没有任何上下文管理**：对话越长，发给 LLM 的历史越多，最终触发模型上下文窗口溢出而瘫掉。
- 现状三处关键事实（代码探查确认）：
  1. **工具结果不跨轮持久**——只在单次 `agent.run(ctx)` 内存活，下一条用户消息重建 `ctx` 时丢弃。
  2. `Delta.usage.input_tokens`（Anthropic 的 `message_stop` 事件）是 LLM 亲测的完整上文大小，但目前在 `chat.py` 被跳过、未保存。
  3. config 无「上下文窗口上限」概念，触发逻辑无基准可依。
- 参考 `ecc/context-budget`：token 估算沿用「code-heavy 用 `chars/4`」的近似原则（不引精确 tokenizer）。

## 目标

- 让 CodePilot 在**有限的 token 预算内长时间干活**，对话累积再多也不会因上下文溢出而瘫掉。
- 通过**两层压缩**：轻量预防（工具结果存盘）+ 重量兜底（LLM 结构化摘要）。
- 优先压缩 token 大头（工具结果）；**用户的原始消息尽量原文保留，不被摘要改写**。
- 前置：先让工具结果**跨轮持久**，压缩才有作用对象。

## 功能需求

### F0（前置·架构改造）：工具结果跨轮持久
- F0.1 工具执行结果（`ToolResult`）在跨用户消息轮之间**保留在会话历史中**，下一条用户消息重建上下文时仍可见，可被后续轮次继续消费。
- F0.2 会话历史按现有 JSONL 机制**可恢复**，`resume` 后用户/助手文本上下文与崩溃前一致。
- **范围决策（2026-10-11）：** resume 的**工具结果**恢复留后续 state，本轮 F0 只做「进程内跨消息轮持久」。理由：需 store.py 扩展存原生 tool_use/tool_result 配对 + resume 重构，且带路径的工具结果本可用 `read` 工具重读，成本低。聚焦本轮主目标（层1/层2/TUI）。
- 说明：F0 是压缩的作用对象；没有 F0，大批大工具结果不会跨轮累积，「压缩大头是工具结果」无从落地。

### F1（层1·单工具结果存盘）
- F1.1 单个工具结果预估 token 数**超过阈值 N** 时，完整内容**写入磁盘文件**，对话历史中只保留**预览片段 + 文件路径**，供模型按需重新读取。
- F1.2 被存盘的工具结果，模型仍能通过既有 `read`/`grep` 类工具按路径**重新获取完整内容**。

### F2（层1·单条消息工具结果合计存盘）
- F2.1 同一条消息内**多个工具结果的 token 合计**超过阈值 M 时，按估算从大到小将工具结果依次存盘，直到合计压到阈值以内。
- F2.2 存盘规则与 F1.1 相同（预览 + 路径）；存盘是**有损压缩**，触发即接受信息被移到磁盘。

### F3（层2·LLM 结构化摘要兜底）
- F3.1 整体对话预估 token **逼近窗口上限**（自动留 13K 安全余量 / 手动 3K）时，调用 LLM 生成**结构化摘要**。
- F3.2 摘要保留**近期原文**：从尾部按 token 往回数，保留约 **1 万 token 或至少 5 条**消息原文；更早的消息被摘要替代。
- F3.3 摘要按几个**固定部分**组织（结构化输出），保证语义完整、可检索。

### F4（摘要 Prompt 约束）
- F4.1 摘要 Prompt **明确禁止模型调用任何工具**。
- F4.2 摘要生成过程分两步：先写**分析草稿**，再写**正式摘要**；草稿用完即弃、不进对话历史。
- F4.3 摘要生成**不消耗/不写入主对话 token**（独立调用，草稿不入历史）。

### F5（压缩后边界消息）
- F5.1 每次压缩后向对话补一条**边界消息**：提示模型若需文件细节请**重新读取**，不要照着摘要脑补代码。

### F6（手动触发 + 熔断）
- F6.1 用户可**手动触发**压缩。
- F6.2 摘要连续失败 **3 次**触发**熔断**，暂停自动压缩，避免死循环（如摘要越压越大或反复失败）。
- F6.3 熔断后提供恢复路径（重试或解除）。

### F7（用户可见·TUI 上下文指示器）
- F7.1 TUI 界面**实时显示当前上下文使用量**（已用 / 窗口上限，可带百分比）。
- F7.2 执行**轻量预防（F1/F2）或重量兜底（F3）压缩后，显示随之实时更新**，反映压缩带来的空间回收。
- F7.3 数据来源与压缩共用同一「token 估算」口径，保证显示与触发判断一致。

## 非功能需求

### N1（Token 估算）
- N1.1 **不引入精确 tokenizer**，用**近似估算**：锚定上一次请求的 `usage.input_tokens`（LLM 亲测），对自那之后**新增的增量**按字符数估算（code 侧重 `chars/4`，prose 侧重 `words×1.3`）。
- N1.2 估算函数为**独立纯模块**，无 LLM 依赖、可单测。
- N1.3 估算允许误差——余量（自动 13K / 手动 3K）正是为吸收误差而设。

### N2（用户原文保护）
- N2.1 **用户输入的消息永远不因压缩而丢失**：层1只动工具结果，层2把 `assistant`/`user` 纳入摘要时**用户消息优先以原文保留**（近期原文区本身保底 1 万 token 或 5 条）。

### N3（配置驱动）
- N3.1 `context:` 配置段显式指定**窗口上限**（如 `window: 200000`），并允许覆盖自动/手动**余量**与 **N/M 阈值**。

### N4（性能）
- N4.1 压缩决策（估算 → 是否触发）在**每次 API 请求前**执行，开销应远小于一次模型调用，不引入可感知延迟。
- N4.2 压缩操作本身（存盘 / 摘要）不得阻塞主对话流程超过合理界限；摘要独立异步。

### N5（健壮性/熔断）
- N5.1 摘要失败不崩应用，连续 3 次熔断（F6.2）。
- N5.2 层1存盘失败（磁盘不可写等）回退为可接受的降级（不存盘、留预览，勿导致对话丢弃）。

## 不做的事

- **不做精确 tokenizer**（不引 transformers/tiktoken 等库）——用 N1 的近似估算。
- **不做摘要策略的机器学习优化**（不根据成功率/回合数建模去「学习最好的压缩时机」）。
- **不做跨会话跨模型的全局 token 预算**——只管理单个活动会话的上下文。
- **不压缩系统提示（System Prompt）源码**——稳定前缀已用缓存断点优化（既有 `state5`），本轮不动它。
- **不做 `context-budget` 那样的静态配置审计**（agents/skills/MCP 静态开销报告）——不同构于运行时滚动压缩。
- **不做工具结果的历史审计/检索 UI**（本轮存盘只为「模型按路径重读」，不建浏览工具结果的全新交互面板）。

## 验收标准

- **AC-F0**：跨两条用户消息，上一条的工具结果仍留在对话上下文中，模型可引用/续读。
- **AC-F1**：单个工具结果 > N token 时，历史只留预览+路径，完整内容在磁盘文件，模型按路径能重读。
- **AC-F2**：同消息多工具结果合计 > M 时，按大到小存盘直至压回阈值内。
- **AC-F3**：历史逼近窗口时触发摘要，旧消息被结构化摘要替代、近期 ≥5 条或 ≥1 万 token 原文保留。
- **AC-F4**：摘要调用带「禁止工具」约束，两条独立消息流程（草稿→正式），草稿不入历史。
- **AC-F5**：压缩后对话含一条边界消息，提示「细节请重读，勿脑补」。
- **AC-F6**：手动可触发压缩；摘要连续失败 3 次进入熔断态、停止自动重试，可解除。
- **AC-F7**：TUI 状态栏显示上下文使用量，轻量/重量压缩后数字实时下降。
- **AC-N1**：估算模块纯函数、无 LLM 依赖，只对增量估算、锚定上次 usage。
- **AC-N2**：任何压缩发生后用户原始消息仍在，未丢失、未被改写。
- **AC-N3**：`context:` 配置可设 window / 余量 / N / M，且生效。
- **AC-N5**：摘要失败不崩应用；连续 3 次熔断。
